# Suspend, resume and a deadline

## Concept

Two fields on a TrainJob control *when* it consumes resources.

**`spec.suspend`.** Set it to `true` and the controller suspends the JobSet it created; the Jobs suspend; **every
pod is deleted**. The TrainJob keeps its configuration and gets the condition `Suspended=True`. Set it to `false`
and fresh pods are created (the condition turns `False` with reason `Resumed`). A TrainJob can also be *created*
suspended and started later. This is how queueing systems work: Kueue creates (or finds) a TrainJob suspended
and flips the field when it admits the workload (lesson 8). Note what suspension is not: the process is killed,
not paused. Without checkpoints a resumed run starts at step 0; with them (lesson 6) it continues.

**`spec.activeDeadlineSeconds`.** A time limit for the whole TrainJob, with the semantics of a Job's field: when
it passes, running pods are terminated, the JobSet is deleted and the TrainJob becomes `Failed` with reason
`DeadlineExceeded`. The clock starts when the TrainJob is created and restarts at each resume. It is set at
creation; it may be added once to a TrainJob that has none and cannot be changed after that. It is the safety net against a stuck run, a crash loop under
`failurePolicy.maxRestarts`, or a forgotten experiment.

The TrainJob's `status.conditions` tell the story: `Suspended`, `Complete`, `Failed` (with a reason and a
message). `kubectl get trainjob` shows a short `STATE`. Other ways to end up `Failed`: the JobSet reached its
`maxRestarts`, or the runtime named in `runtimeRef` is not supported.

## The situation

Three TrainJobs of the runtime `tiny-gpt` exist in namespace `train`:

- `explore`: a long exploratory run (3000 steps), running now;
- `urgent`: 200 steps, seed 9, created with `suspend: true` and waiting;
- `runaway`: a run of a million steps with no limit, running now.

## Your task

1. Suspend `explore`, without deleting it.
2. Resume `urgent` and let it complete.
3. Give `runaway` an active deadline of 20 seconds (any value from 1 to 60 is accepted), so that it is stopped
   by the controller.

`kdrill verify` checks that `explore` is the same TrainJob as before (not recreated), has `suspend: true`, the
condition `Suspended=True`, a suspended JobSet and no pods; that `urgent` is the same TrainJob, is resumed
(condition `Suspended=False`, reason `Resumed`) and completed with 200 steps and seed 9 in its log; and that
`runaway` has a deadline between 1 and 60 s, is otherwise unchanged and ended `Failed` with reason
`DeadlineExceeded`, its pods and JobSet gone. It waits up to 70 s for the runs; `urgent` needs about 20 s after you
resume it.

## Useful commands

    kubectl get trainjobs,jobsets,pods
    kubectl patch trainjob NAME --type=merge -p '{"spec":{"suspend":true}}'
    kubectl patch trainjob NAME --type=merge -p '{"spec":{"activeDeadlineSeconds":20}}'
    kubectl get trainjob NAME -o jsonpath='{.status.conditions}'; echo
    kubectl explain trainjob.spec.activeDeadlineSeconds

## On a real cluster

Use suspension to make room for urgent work, and as the lever for queue managers, schedulers and cost tools; make
sure suspended jobs have checkpoints or are cheap to restart. Deadlines belong in the platform's job templates (a
default `activeDeadlineSeconds` set by a mutating admission policy or generated by your submit tooling) so that
nothing can occupy GPUs indefinitely. `ttlSecondsAfterFinished` in the runtime's JobSet spec cleans up finished
jobs. For long runs also look at the Kubeflow SDK's `wait_for_job_status` and at the TrainJob's
`status.trainerStatus` (progress and ETA, reported by the training code to the controller).
