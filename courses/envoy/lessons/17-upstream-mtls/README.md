# Upstream TLS and mTLS: Envoy as a TLS client

## Concept

TLS between Envoy and a backend is configured on the **cluster**, with a
`transport_socket` holding an **`UpstreamTlsContext`**, the mirror image of
the listener side:

- `common_tls_context.tls_certificates`: the client certificate Envoy
  presents if the server asks for one (that is what makes it **mutual** TLS);
- `common_tls_context.validation_context`: how Envoy checks the server:
  `trusted_ca` (which CA must have signed it) and
  `match_typed_subject_alt_names` (which identity it must carry: a DNS
  name, or a SPIFFE URI in a mesh);
- `sni`: the server name sent in the ClientHello.

Leaving out the validation context is a classic mistake: the connection is
encrypted, but Envoy accepts any certificate, so it protects against
passive sniffing only. Checking the CA but not the name means any service
holding a certificate from that CA can pose as this backend.

Why mTLS matters: the server knows who is calling (the client certificate
is an identity it can authorize), the client knows who it's talking to,
and nothing in the network path can read or change the traffic. Service
meshes give every workload such an identity and make every connection look
like this one; Istio configures exactly these Envoy fields, with
certificates delivered over SDS and rotated every few hours.

`/clusters` and `cluster.<name>.ssl.*` stats (handshakes,
`fail_verify_san`, `fail_verify_error`, `connection_error`) show what
happens on the TLS layer.

## The situation

`payments` (Service port 443) serves HTTPS with a certificate for
`payments`, `payments.lab.svc` and `payments.lab.svc.cluster.local`, and
requires a client certificate signed by the lab CA. Envoy's cluster
`payments` connects to port 443 in plain text. Envoy has its client
certificate `client.crt`/`client.key` (CN `envoy-client`) and the CA
`ca.crt` mounted at `/certs` (Secret `envoy-certs`).

## Your task

Configure the cluster `payments` in the ConfigMap `envoy` so that:

- `GET /pay/...` through Envoy is answered by payments, which saw Envoy's
  client certificate (`CN=envoy-client`);
- Envoy verifies the server certificate with `trusted_ca: /certs/ca.crt` and
  the DNS name `payments.lab.svc.cluster.local`
  (`match_typed_subject_alt_names`);
- Envoy sends SNI `payments.lab.svc.cluster.local`.

## Useful commands

    kubectl exec client -- curl -si http://envoy:10000/pay/42
    kubectl exec client -- curl -sv --cacert /certs/ca.crt https://payments/      # no client cert: refused
    kubectl logs deploy/payments
    kubectl exec client -- curl -s 'envoy:9901/stats?filter=payments.ssl'

When you think you're done: `kdrill verify`

## On a real cluster

The lab CA and certificates are generated by `kdrill start` and live
for one lesson. Real setups get workload certificates from cert-manager,
SPIRE or a mesh CA, rotate them automatically, and push them to Envoy over
SDS rather than files.
