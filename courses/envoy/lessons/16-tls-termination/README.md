# TLS termination with SNI: two sites, two certificates

## Concept

TLS is set up on a listener's **filter chain** as a **transport socket**
(`envoy.transport_sockets.tls` with a `DownstreamTlsContext`): certificate
chain and key, ALPN protocols, protocol versions, and optionally client
certificate validation (mTLS). The HCM above it then sees plain HTTP.

One port can serve many sites with different certificates. The client says
which name it wants in the TLS ClientHello (**SNI**). The
`tls_inspector` **listener filter** reads SNI and ALPN before any filter
chain is chosen, and `filter_chain_match.server_names` selects the chain.
So the selection happens in two stages:

1. **SNI** picks the filter chain: certificate, TLS settings, and the
   network filters (its own HCM and route config);
2. the **Host** header picks the virtual host inside that HCM.

A filter chain without `filter_chain_match` would be the default for
connections that match no other chain; without one, they are closed.

**ALPN** lets client and server agree on HTTP/2 during the handshake
(`alpn_protocols: [h2, http/1.1]`); the HCM (codec `AUTO`) follows.

The plain HTTP listener typically only redirects to HTTPS
(`redirect: {https_redirect: true}`).

Certificates can be files (Envoy reloads them when they change, handy with
a mounted Secret) or come from a control plane over **SDS**, which is how
Envoy Gateway and Istio deliver them.

## The situation

A test CA made the certificates `shop.crt`/`shop.key` (for `shop.lab`) and
`api.crt`/`api.key` (for `api.lab`), stored in the Secret `envoy-certs`
and mounted into Envoy at `/certs`. The client pod trusts the CA
(`/certs/ca.crt`). Envoy only has the plain HTTP listener on 10000.

## Your task

- an HTTPS listener on port 10443: `https://shop.lab:10443/...` reaches the
  shop backend with the `shop.lab` certificate, `https://api.lab:10443/...`
  reaches api with the `api.lab` certificate;
- HTTP/2 is offered with ALPN;
- connections with any other SNI are refused;
- plain HTTP on 10000 for `shop.lab` and `api.lab` answers 301 to the same
  URL on https.

## Useful commands

    kubectl exec client -- curl -sv --cacert /certs/ca.crt --connect-to shop.lab:10443:envoy:10443 https://shop.lab:10443/
    kubectl exec client -- curl -s --http2 -o /dev/null -w '%{http_version}\n' --cacert /certs/ca.crt --connect-to api.lab:10443:envoy:10443 https://api.lab:10443/
    kubectl exec client -- curl -si http://envoy:10000/ -H 'Host: shop.lab'
    kubectl exec client -- curl -s envoy:9901/listeners

`--connect-to NAME:PORT:envoy:10443` makes curl use the name for SNI, Host
and certificate checks while connecting to the envoy Service.

When you think you're done: `kdrill verify`

## On a real cluster

The lab CA and certificates are generated by `kdrill start` (and deleted
by cleanup). In production certificates come from a real CA, usually via
cert-manager (ACME/Let's Encrypt or an internal issuer) into a Secret, and
an edge Envoy sits behind a cloud load balancer that passes TLS through or
terminates it itself.
